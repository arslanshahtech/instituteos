## 5. Security and data-integrity audit (independent findings)

**Strengths (verified in code):**
- Tenant isolation is structural, not cosmetic: membership lookup per request,
  org-first indexes everywhere, 404-masking for non-members, campus scoping.
- Auth is modern for this stack: opaque session tokens (not raw JWTs), CSRF
  protection on mutations, scrypt passwords, session expiry index, 7-day TTL default.
- Money is handled carefully: Decimal128, per-org sequences, unique invoice/receipt
  constraints, bulk-generation skip logic, concession engine, owner-OTP delete shield.
- Secrets hygiene is good: `.env` is git-ignored and untracked; only `.env.example`
  is committed; no secret was found in the tracked tree by this audit.

**Risks / weaknesses:**
1. **Uncommitted work:** 51 tracked files modified (+5,420/−244) plus untracked
   files (import pages, timetable, docs) on `feat/student-import-preview`. Nothing
   is merged or reviewed. Shipping from a dirty tree is the single biggest
   release risk.
2. **Format gate fails:** CI runs `format:check`; 181 files fail it, so a clean
   PR/CI run is currently impossible without a formatting pass.
3. **In-memory rate limiting:** fine for one instance, not shared across instances;
   needs a distributed store before horizontal scaling.
4. **No staging acceptance by this audit:** no browser-verified login, write/read,
   tenant-negative, receipt-reconciliation or persistence-across-restart test was
   run in this session. The pilot plan's go/no-go list is still the right gate.
5. **Backup/restore unproven:** documented as a requirement, never demonstrated.
   Real student data must not be imported before a restore drill.
6. **Import concurrency:** duplicate protection is application-level, not a
   DB-level guarantee for concurrent imports (stated in the pilot plan).
7. **Manual messaging:** WhatsApp links open a prefilled message for a person to
   send. Calling this "automated messaging" would be inaccurate.
8. **No payment gateway, no payroll, no double-entry ledger** — correctly absent,
   but they must not be sold as available.

## 6. Competitor comparison (from inspected research, not vendor claims)

- **Ilham360** (observed read-only 29 Oct + public manual): focused school-office
  workflows — students/families, attendance, monthly fees with skip-existing
  invoices, partial payments, A4 challans, thermal receipts, result publication,
  promotion, Excel import with preview. Its import is plan-gated (Pro/Campus).
  InstituteOS matches its core (students, fees, attendance, exams, import preview)
  but still lacks thermal receipts, family-level payment allocation and daily
  reconciliation.
- **EDUBase** (demo + feature book): far broader — HR/payroll, full accounting,
  library, transport, hostel, canteen, LMS, biometrics. Most of that breadth was
  seen as UI, not tested end-to-end. InstituteOS should **not** chase this
  breadth for Sunday; its advantage is a verified, simple core for one college.
- **InstituteOS position:** strongest in tenant isolation, RBAC scoping, fee
  integrity primitives and college-flexible academics. Weakest in operational
  proof (staging, backup, reconciliation) and in family-level finance workflows.

## 9. Four-milestone delivery plan (user's milestones, realistic sequencing)

### Milestone 1 — Students, Admissions & Families (first)
1. Review and merge the `feat/student-import-preview` branch (or freeze it as the
   release candidate after review); format **only the changed files** in a
   separately reviewed commit.
2. Staging-accept: import preview → row outcomes → duplicate review → confirm →
   summary; sibling/guardian linking; admission→student conversion; duplicate
   handling; export with Urdu UTF-8.
3. Close the import concurrency note with either a DB-level guard or a documented
   single-operator import procedure for the pilot.
4. Exit: import report with verified counts; no silent failures; rollback/retry documented.

### Milestone 2 — Fees, Ledger & Payments
1. Staging-accept: fee structure → bulk generation (skip-existing) → partial/full
   payment → concession → outstanding balance → defaulter list, reconciled to the
   payment receipts for unpaid/partial/paid cases.
2. Implement family-level payment allocation preview (one payment across
   children/months, oldest-due-first) — the largest finance gap vs Ilham360.
3. Add daily cashier reconciliation by payment method.
4. Exit: receipt totals match ledger totals for a full test month; correction path
   uses refunds/corrections, not history deletion (OTP delete stays owner-only).

### Milestone 3 — Receipts, Attendance, Exams & Reports
1. Printable A4 receipt/challan verified in a real browser print; then 58mm/80mm
   thermal layout; receipt reprint audit trail.
2. Attendance staging: class/date flow, bulk mark, corrections, history, role scope.
3. Exams staging: schedule validation (subject must map to class), marks entry,
   publication gating, parent portal published-only results.
4. Reports staging: month-wise, outstanding, defaulter ageing; totals tie to source data.
5. Exit: every report total independently recomputed from invoices/payments.

### Milestone 4 — Security, Optimization, QA & Deployment
1. Independent security re-review (auth lifecycle, tenant/campus negatives, finance
   mutations, OTP throttle, CSRF, rate limits); distributed rate-limit plan.
2. Staging deployment (Vercel frontend, Render API, Atlas replica set), HTTPS,
   secrets, CORS, health/ready, smoke script green.
3. Backup policy + restore drill into a separate test cluster; rollback runbook.
4. Performance pass: bundle audit (already split), slow-query/index review, pagination.
5. Final go/no-go sign-off against Section 8; handover pack (owner/admin, role
   matrix, quick-start, support contact, export/offboarding, known gaps, review date).

**Realistic note:** Milestones 1–4 cannot all reach production-accepted status by
Sunday. Sunday can credibly deliver Milestone 1 + the staging-accepted core of
Milestones 2–3 plus the Milestone 4 release gates for a **controlled pilot**.
Presenting more than that would repeat the exact over-claim this audit warns against.
